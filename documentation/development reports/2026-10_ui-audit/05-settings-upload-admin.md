# UI audit, slice: Settings, Upload, Admin, auth, public pages

Worktree research/ui-audit (origin/dev 77dae73), paths under `frontend/src` unless stated. Nothing was run; every "sees" statement is read from code, and anything not directly in the code is marked inferred.

## 1. Pages and panels

**SettingsPage.tsx** (411 lines). The only configuration page, opened from the avatar menu, for every signed-in role. At 1280x800 (maxWidth 960, l.249): emoji heading "⚙ Settings" plus a two-line explanatory paragraph (250-254); Section "Projects" with another explanatory sentence (258-261), "+ New Project" (264), a DataTable with 5 columns, search box, column picker and CSV/JSON export (272-282; `components/ui/DataTable.tsx` 181-219); Section "Account" (email, "Change password →", 286-297); Section "Integrations" (InaturalistPanel, ApiKeysPanel, 299-302). The Actions column (width 320px, l.186) holds up to 7 outlined emoji buttons per row: 📍 Open, 📊 Health, ✎ Details (admin only, 203), 👥 Members, ⚙ Defaults, 🔔 Notifications, 🗑 Delete (admin only, 233). Per-project panels open one at a time in a 560px right slide-over (318-372), so panels do not repeat per project. Scale: 20 projects is one page (pageSize 50, l.281) of 20 rows x 5 to 7 buttons, i.e. 100 to 140 buttons, each row wrapping to two button lines. The list query embeds `deployments(id)` just to count (44-56), so 20 projects x 100 deployments pulls 2,000 rows per load.

**ProjectDetailsPanel.tsx**: 3 fields (Name, Description, Website) and a Save button enabled only when dirty and valid (89), "Saved ✓" inline (63); admin-only entry.

**ProjectDefaultsPanel.tsx**: 4 selects in a row (235-281), threshold number input with a two-line explanation (286-302), flash mode/LED/From/To plus two more explanation lines (330-368). Every control saves on change (239, 252, 265, 275, 295) with a 2.5 s message (191). Offered to every role (SettingsPage 219-225); a non-admin learns "You need the Project Admin role to change this." only after touching a control (189). Still carries an all-projects mode (163-165, 230-233) that Settings no longer uses.

**NotificationRulesPanel.tsx**: per-user 3 x 3 matrix (22-31), push column permanently disabled (30), species filter input (138-145). Saves on every tick and every keystroke (87-95 → upsert 70-85); the upsert result is ignored, so there is no "saved" and no error. The same "email later, mobile via the app" prose is printed twice: SettingsPage 362-366 and the panel 110-112.

**InaturalistPanel.tsx**: emoji card (🌿), status, two lines of prose, Connect or Sync-all + Disconnect; hidden when `/api/inat/status` 404s, i.e. FF_INAT_ENABLED off (`hooks/useINat.ts` 29-40, panel 203).

**ApiKeysPanel.tsx**: organisation managers only, via `/api/models/managed-orgs` (317-326); hidden when the org list is empty or the key list fails FEATURE_DISABLED (344). Create row (name, expiry, Create), scope checkboxes, one-time key reveal, 7-column table with Revoke via `confirm()` (365).

**components/data/ProjectMembersPanel.tsx**: 5-column members table, Remove (admin, 112, `confirm()` 70), pending invitations table (admin, 130-159), invite form email + role with only Member/Admin offered (184-185) although `ProjectRole` includes `project_viewer` (`lib/projectMembers.ts` 317). `isAdmin` comes from the members list, not `user_roles` (50). 50 members: 50 unsorted, unsearchable, unpaged rows (93-126) in a 560px slide-over. Heading "Members, {projectName}" (82-84) repeats the slide-over header (SettingsPage 327-330).

**components/upload/UploadFlow.tsx** (755 lines), `/upload-data`, RequireAuth + RequireNotDemo (App.tsx 541). Before a folder: one drop zone with two lines (457-479). ## 3. Specific checks

- **Which projects Settings shows**: all non-deleted projects RLS lets the user read, not the top-bar selection (SettingsPage 41-47, 89-94); the picker is only used to navigate on Open (191, 280). An organisation_manager therefore sees every org project (moveDeployment.ts 9-11, inferred from that comment).
- **Panels per project**: none repeat; one slide-over at a time (318-372). ProjectDefaultsPanel and NotificationRulesPanel keep an unused "all projects" mode (ProjectDefaultsPanel 163-165; NotificationRulesPanel 46-48).
- **Flag gating**: no flags endpoint exists (grep for `/api/config`, `features`: none). Panels probe: iNat hides on a 404 from `/api/inat/status` (useINat.ts 36-40), API keys on `FEATURE_DISABLED` from the key list (lib/apiKeys.ts 36-38) or an empty managed-org list, Notifications on a table error (NotificationRulesPanel 55-56). Training reads `/api/models/train/status.enabled` (TrainModelModal 64, 119).
- **UploadFlow states**: before a folder, the drop zone only (455-494); after, tiles + breakdown + notes + AI checkbox + two buttons (497-598); triage replaces the page (431-450). Decisions per unresolved session: one, with three choices (assign, create with name+project, skip).
- **Run AI default**: on (108), server default also on (`backend/app/routers/exif.py` 140). **Can a viewer upload**: yes at the API. `/api/exif/parse` checks only email confirmation and image caps (exif.py 130-200); project access is "any active role on org or project" (`backend/app/authz.py` 44-59), creating a deployment likewise (`routers/deployments.py` 45-60), and the Drive job writes with the service client (`backend/app/jobs/definitions.py` 95-97), so RLS's viewer read-only rule is not applied to uploads (inferred, not run). The AI default is therefore reachable by a viewer; whether that is intended is open question 1.
- **Admin pages**: client gate `useIsAdmin` (has_system_role RPC, hooks/useIsAdmin.ts 215-217) plus backend `require_system_admin` on `/api/admin/devices` (routers/admin.py 17) and a ww_admin-gated RPC for usage (AdminUsagePage header, inferred). Non-admin direct link: heading + "Loading…" then `Navigate to="/"` (finding 20).
- **Login**: two sign-in methods plus the demo; demo is visible but secondary (outlined, under a rule, 93-99), absent on `/signup`. Signed-out `/annotations` → `/login` (App.tsx 65-68, 525).

## 4. Keep

1. The slide-over: one project's settings at a time, with the project named in the header (SettingsPage 318-337).
2. "Where these photos will go" and the honest triage tallies (UploadFlow 523-536; UnassignedTriage 235-243, 291-296).
3. Membership error mapping to plain sentences by SQLSTATE (lib/projectMembers.ts 363-407).
4. Details panel: Save disabled until dirty, shows the row the database returned (ProjectDetailsPanel 46, 60-64).
5. DataTable with search, paging and export on both admin pages, and the org filter on Devices (AdminDevicesPage 422-427).
6. DemoGuard wrapper and toast instead of raw errors (DemoGuard.tsx 319-331); ProgressDock's capped height with a pinned header (ProgressDock 265-277).

## 5. Open questions

1. Is `project_viewer` meant to upload and create deployments? The API allows any role (authz.py 44-59) and `/api/exif/parse` carries no `require_not_demo` (it is absent from the routers that do: brain, camtrapdp, deployments, media, models, pipeline, projects), so the demo's upload block is UI-only (App.tsx 541). If viewers must be read-only, the fix is in ww-backend and the Upload button should hide for them.
2. Do `send_project_invitation` and `remove_project_member` accept a ww_admin who is not a member? The UI assumes not (ProjectMembersPanel 50).
3. Does `notification_rules` RLS let the demo account write? If so, demo visitors edit shared demo state (finding 22).
4. Should "Defaults" be visible to members as read-only (useful context) or hidden (simpler)?
5. Is the CamtrapDP "still needs annotating" mode wanted in the live flow, or can the backend option go?
