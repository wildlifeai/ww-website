## What was there

`e2e/` held four Playwright specs written from the source against the live DOM (smoke, demo
session, SD-card upload with EXIF binding, LoRaWAN realtime). No workflow ran them: they ran
from a laptop against whatever `e2e/.env` named, and the README expected a calibration pass.
`ci.yml` covered lint, pytest with Supabase mocked, vitest and the Vite build;
`backend-integration.yml` was the one check against a real database.

## Decisions

- **Target the Cloudflare Pages preview, not a build on the runner.** Every branch already
  gets a deployed frontend; Cloudflare posts a GitHub deployment per build, and the workflow
  triggers on its success and takes the URL from it. The bundle under test is the one users
  get. Production deployments are skipped: the seeded account lives on dev.
- **Smoke and demo on every preview, upload and LoRaWAN by hand only.** The last two write to
  the dev database and storage.
- **Traces and video off in CI.** A trace records the password typed into the login form, and
  the artifacts of a public repository are public. The failing page's URL, console errors and
  text go into the job log instead (`e2e/helpers/test.ts`).
- **Count what ran.** The specs skip themselves without env; the workflow fails when the junit
  report holds nothing but skipped tests. Same lesson as ww-mobile-app's E2E job, which
  reported green for months while running nothing.
- **Warm the API inside the first test.** The dev API scales to zero; the smoke's API test
  polls `/docs` for up to three minutes so the cold start is not charged to a page test.
- **Accessibility as a separate job**, with axe-core on the public pages, serious and
  critical only. It ran with `continue-on-error` on its axe step until #213 cleared the pages,
  then became blocking. (On the job rather than the step, `continue-on-error` keeps the
  workflow run green but leaves the job's own check red in the pull request.)
- **The seeded account's password comes from a secret the environment already has.** The
  `dev` environment holds `DEMO_PASSWORD` for the backend deploy, which `deploy-backend.yml`
  requires to equal ww-backend's seed password, the one every seeded user signs in with. The
  smoke job takes `E2E_PASSWORD` when set and falls back to `DEMO_PASSWORD`, so no password
  had to be pasted anywhere new. Two runs were lost finding this: the docs named a
  `SEED_USER_PASSWORD` secret that the environment does not have.

   carry the preview URL. `deployment_status` only registers from the default branch, so the
   pull request runs used the `pull_request` trigger against the dev site. If the events do
   not arrive, compute the URL as `https://<branch-slug>.ww-website.pages.dev` and poll until
   it serves.
2. Done: the a11y job is blocking since #213 landed on dev.
3. A hermetic full-stack job beside `backend-integration.yml`: local Supabase from ww-backend,
   this pull request's backend under `uvicorn`, `vite preview`, the smoke against localhost.
   The only E2E that tests the backend half of a pull request; the candidate for a required
   check. Written as `.github/workflows/e2e-full-stack.yml` (#216), described in
   [`e2e/README.md`](../../e2e/README.md#in-ci); its first run is the first pull request that
   carries it. Its `paths` filter became a `changes` job (#215), so it reports on every pull
   request and can be required: it is skipped, not missing, when none of its paths changed.
4. Done in #217, waiting on its first run from `main`: the full suite after each dev backend
   deploy and nightly, with `e2e/cleanup.mjs` after it. Writing the cleanup showed the
   LoRaWAN spec had never run in CI: its insert left out `device_eui` and `raw_payload`, both
   NOT NULL, and named the parsed row's foreign key `message_id` instead of
   `lorawan_message_id`. Fixed in the same change, and its rows now carry the run's tag.
5. Cheap checks: an OpenAPI snapshot diff, a docs link validator like ww-mobile-app's, advisory
   `npm audit` and `pip-audit`.
6. Make the smoke required after a green week.
